# POC 범위와 마일스톤

## 목적

Wecovi POC는 TypeScript 정적 분석으로 함수의 실행 흐름을 정확하게 구성하고, WebStorm 안에서 그 흐름을 단계적으로 탐색할 수 있는지 검증한다.

첫 사용자는 플러그인 개발자 본인이다. 따라서 별도의 사용자 조사나 정량 사용성 지표보다 분석 결과의 정확성과 실제 사용 시의 개인적인 효용을 기준으로 판정한다. 기능의 정확한 동작은 필수이고, 편의 기능은 POC 이후로 미룰 수 있다.

## 결정 사항

### 검증 전략

- 일반 TypeScript fixture에서 분석 기능을 단계별로 구현하고 테스트한다.
- 모든 분석 단계가 통과한 뒤 별도의 실제 NestJS 프로젝트에서 대표 endpoint 흐름을 최종 검증한다.
- NestJS 검증 대상 프로젝트 경로와 endpoint는 최종 검증 전에 지정한다.
- POC의 공식 flow 시작점은 `@covi-root`가 붙은 함수로 한정한다.
- NestJS Controller endpoint 자동 탐지는 POC 범위에 포함하지 않는다.

### 성공 기준

POC 성공은 다음 정보를 실제 코드와 일치하게 표시하는 것으로 판정한다.

- 함수 호출 순서와 호출할 때 전달된 인자
- `await`와 `return`
- 조건 분기, 예외와 반복 구조
- 순차 실행과 지원 대상 병렬 실행의 구분
- 프로젝트 내부 함수와 외부 라이브러리 함수의 구분
- 재귀 호출의 경계
- interface 구현체와 런타임 DI 경계

분석 결과가 정확하면 흐름을 이해하는 사용성도 함께 확보될 것으로 기대한다. POC에서는 시간 단축률이나 파일 이동 횟수 같은 별도의 정량 지표를 필수 성공 조건으로 두지 않는다.

### 정확성 원칙

- 코드에서 확정할 수 없는 호출 관계를 추측해서 연결하지 않는다.
- 누락되거나 중단된 흐름은 허용하지만 잘못된 연결은 허용하지 않는다.
- 호출 대상을 확정하지 못하면 원본 표현식과 `Unresolved` 상태를 표시하고 해당 경계에서 분석을 멈춘다.
- interface 구현체 후보가 여러 개이면 `Multiple` 상태로 표시하되 임의의 구현체로 연결하지 않는다.
- 런타임 DI로 결정되는 호출은 `Runtime binding` 경계에서 멈춘다.
- 각 마일스톤은 전용 fixture의 기대 흐름과 실제 분석 결과를 비교하고, 이전 마일스톤의 회귀 테스트를 함께 통과해야 완료된다.

## POC 필수 UX

- `@covi-root` 기반 Flows 목록
- `@covi`와 `@covi-root` 기반 Functions 목록
- 선택한 flow의 읽기 전용 Flow Canvas
- root 함수의 상위 흐름 표시
- 호출된 프로젝트 함수 노드의 중첩 펼치기
- 프로젝트 내부, 외부, 미해결, 재귀와 다중 구현체 상태 구분
- 노드에서 원본 코드 위치로 이동

Flow 검색·필터, 확대·축소, 화면 맞춤과 상세 미리보기 같은 편의 기능은 핵심 탐색을 구현하는 데 필요한 최소 수준만 제공한다.

## 마일스톤

### M1. 기본 호출 흐름

구현 및 검증 대상:

- `@covi-root`와 `@covi` 함수 탐색
- 일반 함수와 이름 있는 arrow function
- 함수 호출 순서
- 호출 인자 표현식과 함수 시그니처
- `await`와 `return`
- 프로젝트 내부 함수와 외부 라이브러리 함수 구분
- Flows/Functions 목록, Flow Canvas, 노드 펼치기와 소스 이동의 최소 동작

완료 조건은 fixture의 호출 순서와 경계가 잘못된 연결 없이 Canvas에 표시되는 것이다.

### M2. 제어 흐름과 예외

구현 및 검증 대상:

- `if/else if/else`
- `switch/case`
- `throw`
- `try/catch`
- `for`, `for...of`, `while` 등 반복문

완료 조건은 분기와 정상·예외 경로가 소스의 중첩 및 실행 순서와 일치하고, 반복 실행을 노드 복제가 아닌 반복 블록으로 표시하는 것이다.

### M3. 비동기 그룹과 재귀

구현 및 검증 대상:

- 배열 리터럴 형태의 `Promise.all`
- 병렬 실행 그룹
- 직접 재귀와 간접 재귀
- `Recursive` 경계 처리

완료 조건은 지원 대상 병렬 호출을 순차 호출과 구분하고, 재귀 흐름을 무한히 확장하지 않는 것이다. 동적으로 구성한 Promise 배열과 복잡한 Promise 조합은 POC 제외 범위를 유지한다.

### M4. interface 구현체와 DI 경계

구현 및 검증 대상:

- interface의 단일 구현체 탐색과 연결
- 다중 구현체의 `Multiple` 상태 표시
- 구현체가 없는 interface 경계
- `@Inject(TOKEN)`, factory provider와 조건부 provider 등의 `Runtime binding` 경계

완료 조건은 정적으로 단일 구현체를 확정할 수 있을 때만 연결하고, 그 외에는 추측 없이 경계에서 멈추는 것이다.

### M5. 실제 NestJS 프로젝트 검증

사전에 별도 NestJS 프로젝트와 대표 endpoint 하나를 지정한다. Controller handler에 `@covi-root`를 추가하고 Controller에서 시작해 Service, Repository 또는 외부 의존성까지 이어지는 흐름을 검증한다.

완료 조건은 M1~M4에서 지원한 구문과 경계가 실제 프로젝트에서도 잘못된 연결 없이 표시되고, 개발자 본인이 코드의 주요 실행 순서와 성공·실패 조건을 Canvas에서 파악할 수 있다고 판단하는 것이다.

## POC 이후 후속 작업

다음 항목은 POC 완료 후 별도 마일스톤으로 진행한다.

### F1. Covi 메타데이터 편집

- Inspector에서 함수 설명 편집
- `@covi`, `@covi-root`, `@covi-group` 추가 및 변경
- 조건, 대입과 `return` 등 지원 문장의 Covi 설명 편집
- TypeScript 소스에 변경 내용 저장
- WebStorm write action과 Undo 연동
- 저장 결과를 Flow Canvas에 반영

NestJS endpoint 자동 탐지와 다중 구현체 후보를 사용자가 선택해 임시 flow로 여는 기능도 POC 결과를 확인한 뒤 후속 범위에서 검토한다.
