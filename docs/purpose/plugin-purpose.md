# 코드를 파일이 아니라 실행 흐름으로 읽는 WebStorm 플러그인

## 한 줄 요약

Wecovi는 AI가 빠르게 작성한 TypeScript 코드를 모든 파일과 구현문을 따라가지 않고도, **기능이 어떤 순서와 조건으로 동작하는지 한눈에 이해하도록 돕는 WebStorm 플러그인**이다.

## 왜 이 플러그인이 필요한가?

AI를 활용하면 코드를 작성하는 속도는 빨라진다. 그러나 생성된 코드의 구조와 실행 흐름을 이해하는 속도까지 같은 비율로 빨라지지는 않는다. 개발자는 하나의 기능을 파악하기 위해 Controller, Service, Repository, Entity와 외부 라이브러리 구현을 여러 파일에 걸쳐 오가야 한다.

문제는 코드가 많다는 사실 자체가 아니다. 사용자가 알고 싶은 것은 대개 다음과 같은 질문의 답이다.

- 이 요청은 어디에서 시작하는가?
- 어떤 함수가 어떤 순서로 호출되는가?
- 성공과 실패는 어떤 조건에서 갈라지는가?
- 데이터는 언제 생성되고 저장되는가?
- 최종적으로 무엇을 반환하는가?

Wecovi는 이 질문에 답하는 데 필요하지 않은 구현 세부사항을 접고, 필요한 순간에만 펼쳐 볼 수 있게 한다.

## 기존에는 어떻게 코드를 읽었나?

회원가입 기능을 확인한다고 가정하면 개발자는 endpoint에서 시작해 호출되는 함수를 따라 여러 파일을 이동한다.

```text
Controller
  → UserService
    → UserRepository
      → UserEntity
    → TermsRepository
  → Response
```

IDE의 선언으로 이동과 사용처 찾기는 정확하지만, 한 번에 하나의 위치만 보여준다. 호출 단계가 깊어질수록 처음 시작한 기능과 현재 보고 있는 코드의 관계를 머릿속에서 계속 유지해야 한다. 분기, 예외, 반복, 비동기 호출이 섞이면 이 부담은 더 커진다.

## Wecovi에서는 무엇이 달라지는가?

Wecovi는 파일 목록 대신 사용자가 선택한 기능의 실행 흐름을 먼저 보여준다.

```text
회원가입 signup(id: string, pw: string)
  1. ID 중복 사용자 검증
  2. User 생성
     2-1. UserEntity 생성
     2-2. password 설정
     2-3. UserEntity 저장
     2-4. 예외 처리
  3. 사용자 약관 저장
  4. userId 반환
```

`User 생성`처럼 다른 프로젝트 함수로 이어지는 노드는 처음에는 접혀 있다. 사용자가 노드를 펼치면 내부 흐름이 같은 화면에 나타난다. 따라서 전체 구현을 한꺼번에 읽지 않고도 큰 흐름에서 세부 흐름으로 단계적으로 들어갈 수 있다.

| 관점 | 기존 코드 탐색 | Wecovi |
| --- | --- | --- |
| 시작점 | 파일이나 symbol을 직접 찾음 | 등록된 flow와 함수 목록에서 선택 |
| 탐색 단위 | 파일과 함수 선언 | 기능의 실행 순서 |
| 호출 관계 | 이동하면서 기억 | 연결된 노드로 유지 |
| 세부 구현 | 즉시 전체 코드 노출 | 필요할 때만 펼침 |
| 설명 | 함수명과 코드에서 추론 | Covi 설명을 우선 표시 |
| 원본 코드 | 에디터에서 확인 | 상세 패널과 소스 이동으로 확인 |

## 어떤 정보를 보여주는가?

Wecovi는 TypeScript 정적 분석을 통해 다음 정보를 추출한다.

- 함수명과 함수 시그니처
- 호출할 때 전달한 인자 표현식
- 반환 타입과 return 문
- 동기·비동기 함수 호출과 `await`
- 조건 분기와 `switch`
- 반복문
- `try/catch`와 `throw`
- 프로젝트 내부 함수와 외부 라이브러리 함수의 경계

코드에서 자동 추출한 정보는 사실 정보로 취급해 읽기 전용으로 보여준다. 사람이 더 읽기 쉬운 이름과 그룹을 제공하고 싶을 때는 Covi 메타데이터를 사용한다.

```ts
/**
 * 회원가입
 *
 * @covi-root
 * @covi-group 사용자 API/User
 */
async signup(id: string, pw: string): Promise<number> {
  // ...
}

/**
 * 사용자를 생성하고 저장한다.
 *
 * @covi
 */
async createUser(id: string, pw: string): Promise<UserEntity> {
  // ...
}
```

- `@covi-root`는 공식 flow의 시작점을 등록한다.
- `@covi-group`은 `/`로 구분한 메뉴 경로를 지정한다.
- `@covi`는 내부 함수를 독립적으로 검색하고 시각화할 수 있게 한다.
- 그룹이 없는 `@covi` 함수는 `Ungrouped`에 표시한다.
- Covi 설명이 없으면 실제 함수명이나 코드 표현식으로 대체한다.

## 왜 코드 분석과 사람의 설명을 함께 사용하는가?

호출 관계를 모두 사람이 작성하면 실제 코드가 바뀔 때 문서가 쉽게 오래된 상태가 된다. 반대로 코드 분석만 사용하면 `create`, `validate`, `save` 같은 함수명이 비즈니스 의미를 충분히 전달하지 못할 수 있다.

Wecovi는 두 책임을 나눈다.

| 책임 | 정보의 출처 |
| --- | --- |
| 실제 호출 관계와 타입 | TypeScript 코드 정적 분석 |
| 사람이 읽을 노드 설명 | Covi 메타데이터 |
| flow 시작점과 메뉴 그룹 | `@covi-root`, `@covi-group` |
| 원본 구현 | 프로젝트 소스 코드 |

연결선은 코드에서 다시 계산하고, 설명은 소스에 가까운 JSDoc과 Covi 주석에 둔다. 시각화만을 위한 별도의 flow 파일을 진실의 원본으로 만들지 않는다.

## 첫 번째 지원 범위

첫 버전은 TypeScript 프로젝트를 대상으로 한다. NestJS Controller endpoint를 대표 사용 사례로 검증하지만, 내부 분석은 특정 프레임워크에 묶이지 않는 것을 목표로 한다.

범용 TypeScript 함수는 `@covi-root`를 시작점으로 등록할 수 있다. NestJS에서는 Controller handler에 같은 메타데이터를 작성해 endpoint 기준 flow를 구성한다.

외부 라이브러리 함수는 내부 구현까지 펼치지 않는다. 라이브러리명과 호출 가능한 interface 또는 signature만 보여줘 프로젝트 코드와 외부 코드의 경계를 분명하게 한다.

## 함께 제공할 AI 작성 가이드

플러그인과 함께 Claude와 Codex용 `SKILL.md`를 제공한다. Skill은 다음 작업을 돕는다.

- 기능의 시작 함수에 `@covi-root`와 그룹 추가
- 호출되는 프로젝트 함수에 `@covi` 설명 추가
- 중요한 분기와 문장에 사람이 읽을 설명 추가
- 기존 Covi 설명과 코드 동작 보존
- 누락되거나 잘못된 Covi 메타데이터 확인

AI는 실행 흐름 자체를 별도 문서로 복제하지 않는다. 코드 구조는 플러그인이 분석하고, AI는 사람이 읽을 설명을 소스 가까이에 남기는 역할을 맡는다.

## 성공 기준

첫 버전은 다음 질문에 기존 파일 탐색보다 적은 이동으로 답할 수 있어야 한다.

- 선택한 endpoint가 어떤 함수들을 호출하는가?
- 현재 함수 내부의 주요 단계는 어떤 순서로 실행되는가?
- 어느 조건에서 성공과 실패가 갈라지는가?
- 호출 대상이 프로젝트 코드인지 외부 라이브러리인지 구분되는가?
- 노드 설명이 부족할 때 같은 화면에서 Covi 정보를 보완할 수 있는가?
- 필요한 순간 원본 함수와 전체 코드를 확인할 수 있는가?

목표는 코드를 보지 않게 만드는 것이 아니다. **먼저 흐름을 이해하고, 필요한 코드만 정확히 찾아 읽게 만드는 것**이다.

## 첫 버전에서 다루지 않는 것

- 실제 런타임 값과 실행 추적
- AI가 생성한 호출 관계를 사실처럼 표시하는 기능
- 외부 라이브러리 내부 구현 시각화
- 동적으로 조합된 복잡한 `Promise` 흐름
- 소스와 별도로 유지되는 수동 flow diagram

이 항목들은 정적 분석 기반의 기본 경험이 유용하다는 사실이 확인된 뒤 검토한다.
